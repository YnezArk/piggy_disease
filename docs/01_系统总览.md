# 01 系统总览与指标口径

> 项目：音识咳 · 猪咳嗽声智能监测与诊疗辅助决策系统  
> 更新：2026-10-25  
> 本文是整套材料的**主入口**：先看架构、数据、指标口径，再按需读模块文档。

---

## 1. 一句话概括

麦克风采集猪舍声音 → **监测模块**识别咳嗽事件并统计频次 → **辨病模块**用声学特征判断疾病类别 → **论治模块**用 RAG + 大模型完成辨证、组方、安全校验。

```text
音频采集
  └─ monitor/       咳嗽/非咳嗽二分类，输出事件时间戳、频次、预警级别
      └─ diagnosis/ 84 维声学特征 → 6 类疾病 + 置信度
          └─ prescription/ 疾病 + 症状/体温/体重 → 证型/治则/方剂/剂量/校验
              └─ MySQL / API / 前端展示
```

| 模块 | 回答的问题 | 核心技术 | 主要输出 |
|---|---|---|---|
| `monitor/` | 有没有咳嗽、咳了几次 | MFCC 39 维 + CNN-BiLSTM | 咳嗽事件、频次、`normal/warning/danger` |
| `diagnosis/` | 可能是什么病 | 84 维多域特征 + SSLRB 集成 | `label`、`disease`、`confidence`、`top3` |
| `prescription/` | 是什么证、开什么方 | RAG 三库 + Qwen 三阶段 + 规则引擎 | 证型、治则、组方、剂量、禁忌、出处 |

三个模块通过 JSON 契约解耦；`diagnosis/bridge.py` 是辨病到论治的唯一转换点。

## 3. 指标总表（先看口径，再看数字）

### 3.1 监测模块

| 口径 | 评估对象 | 结果 | 证据 |
|---|---|---|---|
| 片段级留出测试 | 54 个留出文件切出的 177 段，基础配置 | Acc **96.61%**；Macro-F1 **96.22%**；咳嗽 P/R/F1 **97.44%** | `results/monitor/evaluation_report.json` |
| 文件级严格对比 | 同样的 54 个留出文件，基础 vs 调参 | 基础 Acc 88.89% / F1 0.914；调参 Acc **92.59%** / F1 **0.944**，误报均为 2 | `results/monitor/tuned/公平对比_测试集.md` |
| 全量回测（in-sample） | 540 个文件，调参方案 | Acc **98.15%**；F1 **0.986** | `results/monitor/tuned/对比_原方案_vs_调参方案.md` |

|---|---|---|---|

## 4. 关键设计决策

| 决策 | 原因 |
|---|---|
| 监测用 CNN-BiLSTM，辨病用 84 维 + SSLRB | 监测是“片段是否咳嗽”的时序判别；辨病样本极少（13–49 条/类），低维可解释特征 + 集成学习更稳 |
| 辨病主指标用 Macro-F1 | 类别极不平衡，Accuracy 虚高 |
| 论治用 RAG + 现成 LLM，不从头训练 | 知识密集型任务，依赖权威知识而非海量标注 |
| 小库全量注入、大库向量检索 | 辨证库 11 条、论治库 14 首全量仅约 3.5k token；典籍库 230 段用 Top-5 |
| 安全校验用规则引擎，不用 LLM | 剂量/配伍/孕猪禁用必须确定性判断 |
| 辨病结果只作参考，证候跟症状走 | 同病异证；上游模型可能错，论治层做双重交叉验证兜底 |

## 5. 已知边界

1. **数据规模小**：六类最少 13 条；跨猪场/设备泛化未验证。
2. **监测指标分口径**：片段级高于文件级；对外汇报优先使用文件级严格留出 92.59%。
3. **辨病 5 折上 SVM 高于 SSLRB**：SSLRB 的优势在独立测试 Macro-F1（0.7516）与不平衡场景，不能写成“全面优于 SVM”。
4. **论治知识库有限**：辨证 11 条、方剂 14 首；复杂/混合感染覆盖不足。
5. **安全规则有缺口**：十九畏未入库、未入库药材不校验、孕猪仅提示。
6. **LLM 依赖外部网关**：网络/配额/模型版本会影响演示；已通过关闭思考模式把端到端降到约 30 s。

## 6. 答辩速答（10 条）

**Q1：为什么监测用 CNN-BiLSTM，辨病不用？**  
监测是 101 帧×39 维的时序判别，CNN 提局部频谱、BiLSTM 建时序；辨病每类只有 13–49 条，端到端深网容易过拟合。我们做了同数据同 5 折的 CNN 对照：CNN-BiLSTM(logFBank) 0.700±0.061，SSLRB 0.726±0.032，SVM 0.761±0.043。结论是“当前数据条件下 CNN 不占优”，不是“CNN 不行”。

**Q2：SSLRB 是什么？**  
两层堆叠：第一层 3 个 RBF-SVM（C=100，γ=0.1/0.01/0.001）用 3 折 OOF 生成 18 维元特征；第二层 3 个逻辑回归做 Bagging，并用 ROS 缓解不平衡；最后概率平均。

**Q3：监测指标到底是多少？**  
分三个口径：片段级留出 96.61%；文件级严格留出 92.59%（F1 0.944）；全量回测 98.15%。对外主用 92.59%，因为最接近真实泛化。

**Q4：92.8%/97.4% 是你们的吗？**  
不是。那是纪楠论文的文献值，只用于背景对比。本项目监测真实值是上面的 96.61/92.59/98.15。

**Q5：样本这么少，怎么防过拟合？**  
监测：数据增强（时间拉伸/音高/加噪/时移）、按样本 ID 分层划分防泄漏、Dropout、早停、特征标准化。辨病：低维特征、ROS、Bagging、5 折均值±标准差报告。

**Q6：为什么用 LLM，不怕胡说？**  
三件事：检索片段必须带出处，检索为空时标注“缺检索依据”；剂量/配伍/孕猪禁用走规则引擎；校验不通过则拦截并提示人工审核。LLM 只做知识推理，不做安全判断。

**Q7：辨病错了怎么办？**  
论治层双重交叉验证：规则库按症状/体温查全部命中规则，与上游病名做别名归一比较；LLM 再独立判断一次。只有“没有任何规则支持上游病名”才标 `conflict=true`，有同病规则则弱化为“多病可能”。

**Q8：怎么保证用药安全？**  
剂量 = 基础剂量 × 体重系数（0.7/1.0/1.3/1.5）× 病情系数（0.8/1.0/1.2），仅灌服类换算；超区间上限 8 倍硬拦截；配伍禁忌硬拦截；孕猪慎用软提示。237 张问题处方审计拦截 98.7%。

**Q9：系统怎么部署？**  
监测：Docker + Flask，8000/5000 端口；论治：FastAPI 8000 端口；模型训练在本地，推理在服务端。训练重、推理轻。

**Q10：最大的不足？**  
数据规模和场景覆盖。下一步优先级：多猪场/多设备采集 → 留一猪场/设备验证 → 主动学习回流 → 预训练音频模型迁移。辨病继续扩 prrs/app/other_disease；论治扩三库并补十九畏。
